# REVIEW-PERSONAS.md — pos-module-common-styling

Review frameworks for evaluating components, tokens, and design system output. See `RULES.md` for the project rules.

When reviewing a component, token set, or any design system output, apply the relevant persona(s) below. Each persona has a defined scope, checklist, and output format.

**Two personas are not optional: Component Spec / Tokens Panel QA Reviewer, and Security & Risk Reviewer.** Every other persona below is applied when a review is requested or the situation calls for it. These two are different — mandatory, automatic self-checks, not a review someone has to remember to ask for. Run the QA one every time a component's CSS, JS control wiring, or `tokens/components/<name>.json` spec is created or edited; run the Security one on every change to this repo, before reporting the work done. See each one's own section for its full rule and the reason it exists.

---

### Accessibility Auditor

Evaluate every component as if it will be used by someone relying on a screen reader, keyboard navigation, or assistive technology.

Always check:
- Semantic HTML structure and correct ARIA roles
- Full keyboard operability and logical tab order
- Visible focus indicator present and token-driven
- Focus trap and restore behavior for modals and overlays
- All form inputs have labels; icon-only buttons have `aria-label`
- Error and validation states announced to screen readers
- Text contrast minimum 4.5:1; interactive element contrast sufficient
- Color is never the sole means of communicating state
- Default interactive elements meet 44px minimum touch target
- Small variants flagged as desktop-only

Output format:
```
Accessibility Review — [Component]
Critical issues: ...
Warnings: ...
Passed: ...
Verdict: Pass / Needs improvement / Fail
```

### Token Architect

Evaluate token usage and structure with strict hierarchy enforcement.

Always check:
- No hardcoded values anywhere
- No primitive tokens used directly in components
- Semantic tokens correctly reference primitives
- Component tokens correctly reference semantic tokens
- Token names are role-based and consistent
- All token categories covered: color, typography, spacing, size, radius, shadow, border
- Responsive/device modes defined where needed
- Light and dark mode variants defined where applicable
- No duplicate or redundant tokens
- Missing tokens flagged with proposed name and value

Output format:
```
Token Review — [Component]
Hierarchy violations: ...
Hardcoded values: ...
Missing tokens: ...
Passed: ...
Verdict: Pass / Needs improvement / Fail
```

### Design System Expert

Evaluate architectural integrity, consistency, and long-term scalability.

Always check:
- Component is headless and framework-agnostic
- All required states and variants are defined
- Composition used where existing components apply — and only the variants / optional elements a component documents (`components/<name>.json` › `variants`, `props`, `usageExample`; its docs page Options); nothing added to a component that it doesn't offer
- Naming is consistent with the rest of the system
- Full theming support through tokens — no structural changes needed for brand customization
- Component is scalable and documentable
- No patterns that duplicate existing system decisions
- **Basic UI best practices on the rendered result** (mandatory for every visible change — `ui-design-review` › *Layout & UI basics*): breathing room between text and boxes, no touching / overlapping elements, items in a row aligned (measure 1–2px offsets), consistent spacing rhythm, no unwanted wrapping or overflow, clear hierarchy, controls that look and work like controls. Render it and look at a screenshot; propose the best-practice fix for each problem.

Output format:
```
Design System Review — [Component]
Layout & UI basics: ...
Architecture issues: ...
Composition opportunities: ...
Missing states or variants: ...
Naming issues: ...
Theming concerns: ...
Strengths: ...
Verdict: Pass / Needs improvement / Fail
```

### Figma–Code Parity Reviewer

Evaluate alignment between Figma and code when both exist.

Always check:
- Token names and values identical in Figma and code
- Same states defined in both environments
- Same variants defined in both environments
- No hardcoded values in Figma (all use Figma variables)
- Component and variant naming consistent across both
- Git token files are the source of truth when values differ

Output format:
```
Figma–Code Parity Review — [Component]
Token mismatches: ...
Missing states: ...
Missing variants: ...
Hardcoded values in Figma: ...
Naming inconsistencies: ...
Recommended action: ...
Verdict: Pass / Needs improvement / Fail
```

### AI Readiness Reviewer

Evaluate whether the component and system can be reliably understood and generated by AI tools.

Always check:
- Tokens are machine-readable and consistently structured
- Component definitions include all required fields explicitly
- Naming is consistent enough for pattern inference
- Documentation is explicit — no implied knowledge
- Rules are stated as clear, verifiable constraints
- File structure is predictable and navigable
- An AI tool could generate a compliant component from the design system rules and token definitions alone

Output format:
```
AI Readiness Review — [Component]
Ambiguities: ...
Missing information: ...
Naming inconsistencies: ...
Documentation gaps: ...
Strengths: ...
Verdict: AI-ready / Needs improvement / Not AI-ready
```

### Component Spec / Tokens Panel QA Reviewer — MANDATORY, run automatically

**This persona is not optional and not on-request.** Every other persona in this file is applied when someone asks for a review. This one runs by default, every single time a component's CSS, its control-wiring JS, or its `tokens/components/<name>.json` spec is created or edited — as a self-check before the work is reported as done, not as a separate task someone has to remember to trigger.

**Why:** the rules in `RULES.md` §7 (swatches, combined Intent × State keys, `composedOf`, disabled State controls, the `role` field) are easy to break silently; this checklist forces the check before the work is called done.

**Ground rule: verify against the real files, never from memory or assumption.** Every checklist item below requires actually reading the current CSS, the current spec JSON, and (for the swatch check) the live resolved token value — not recalling what a similar component did last time.

Always check, against `RULES.md` §7's full rule set:

- **Full token listing (7.6)** — every `--pos-*` custom property the component's real CSS applies, across every variant × state, appears in the spec. `figma: null` is correct and required when no Figma name exists — never omit the token because of that, never invent a name to fill the gap.
- **Typography pair (7.2)** — if a font-family token is listed anywhere, the matching font-size token is listed alongside it in the same section, and vice versa. Never one without the other.
- **Swatch — value-based only (7.7)** — for every token, resolve its live value (`getComputedStyle(document.documentElement).getPropertyValue(css)`, matching `isSwatchEligible()`'s own hex/`rgb()`/`rgba()`/`hsl()`/`hsla()` test) and confirm `swatch` is explicitly `true` when it resolves to a color and explicitly `false` otherwise. Never decide by section heading ("Elevation" is not automatically excluded) or by name prefix (`--pos-color-*` is not reliable on its own).
- **Full state listing, not a diff (7.9)** — every state's token list is everything visually applied while that state shows, including tokens unchanged from `normal`. A state block that only lists what changed is wrong even if every listed token is individually correct.
- **Combined-dimension completeness (7.11)** — if the component has an Intent (or any second) dimension alongside State, every dimension × state combination that the UI lets someone select has its own real spec entry. Trace `getGenericVariantSections()`'s (or the component's bespoke equivalent) actual fallback order and confirm no reachable combination silently renders a different state's tokens.
- **Composed-of, not duplicated (7.12)** — if the component's real markup instantiates another DS component, that component's own tokens are declared via `composedOf`, never copied into this spec directly.
- **Missing-state gating (7.13)** — if any variant/kind has fewer states than the component's full state set, confirm the actual JS disables the State controls for the states that variant/kind doesn't have (don't just check the JSON — open `src/js/styleguide-component-page/controls/status-size-scheme.ts` and confirm the gating code exists and is wired to the right toggle).
- **`role` field survives (7.14)** — grep every token-display mapper function the component's Tokens panel can go through and confirm none of them drop `role` while reshaping the token object.
- **CSS-reference sync (7.8)** — if any CSS token *reference* was changed in this same edit, grep `tokens/components/` for the old token name — zero remaining hits.
- **Spec ↔ partial byte-sync** — the generated `spec-<name>.liquid`'s embedded JSON is byte-identical to the source `tokens/components/<name>.json` (Node `JSON.stringify` comparison, per `RULES.md` §6.4) — never hand-edited, always regenerated.
- **Render include actually present (7.16)** — `grep "style-guide/spec-<key>'" component-template.liquid` returns exactly one match. A spec JSON and its `spec-<name>.liquid` partial existing on disk mean nothing if this line is missing: `COMPONENT_SPECS[key]` never populates, and the Tokens panel/code snippet silently fall back to broken legacy data with no error anywhere. Never assume this line exists just because the spec files do — it is a separate, easy-to-forget manual step even in the scripted creation flow.
- **`{% raw %}` wrapper present (7.17)** — the generated partial's JSON is wrapped in `{% raw %}...{% endraw %}`, not a bare `<script type="application/json">`. Without it, any literal Liquid-looking text in a string field (`usageExample` especially) gets executed as real template code the moment the spec is actually rendered, breaking the page.
- **Rendered, not just authored** — open the actual Tokens panel for at least one affected variant × state and visually confirm it, not just re-read the JSON. A correct field can still render wrong if the display path itself has a bug.

Output format:
```
Spec QA Review — [Component]
Full token listing:        Pass / Gaps: ...
Typography pair:           Pass / Gaps: ...
Swatch correctness:        Pass / Gaps: ...
Full-state (not diff):     Pass / Gaps: ...
Combined dimensions:       Pass / Gaps: ...
Composed-of:               Pass / N/A / Gaps: ...
Missing-state gating:      Pass / N/A / Gaps: ...
Role field preserved:      Pass / Gaps: ...
CSS-reference sync:        Pass / N/A / Gaps: ...
Spec/partial byte-sync:    Pass / Fail
Render include present:    Pass / Fail
Raw wrapper present:       Pass / Fail
Live-rendered check:       Pass / Gaps: ...
Verdict: Pass / Needs fixes (list them) / Fail
```

A `Verdict: Pass` is a precondition for reporting the component task done — a `Needs fixes` or `Fail` verdict means the fixes happen before the task is reported complete, not after, and not only when the user happens to notice from a screenshot.

### Security & Risk Reviewer — MANDATORY, run automatically

**Not optional and not on-request** — same standing as the QA persona above. Run this against every change made in this repo (any commit being prepared, any new file, any dependency or external-resource addition), before reporting the work done. This is scoped to this specific repo's actual risk surface, not a generic "be careful" reminder — Claude Code's own built-in safety behavior (confirming before destructive git operations, never entering credentials, flagging secrets) already applies everywhere and doesn't need restating here; this persona covers what's specific to a design-system module like this one.

Always check:

- **Icons come only from the generator.** `icon.liquid` is generated from `tokens/icon-registry.json` (`npm run build:icons`, Tabler Icons, MIT) — flag any hand-edited `<svg>` in it, any icon SVG pasted into another partial, and any icon name used in markup that the registry doesn't have. The local `icons/` folder (licensed Streamline sources for the Figma file) is gitignored and must never be copied into a tracked file.
- **No secrets or credentials ever committed.** Before staging, check `git status`/`git diff` output for anything that looks like an API key, token, password, `.env` file, or personal access token — including inside scratch scripts, config examples, or code comments left in from debugging. This module has no server-side secrets of its own, but Figma tokens, MCP credentials, or copy-pasted debug output can end up in a file by accident.
- **The old DS stays off this branch, and nothing outside this module changes — verify, don't assume.** Before any commit: no old-DS file (the old CSS, the old `/style-guide` page, its layout or init) has been re-added from `master` or history, and `git status` / the diff touches nothing outside `pos-module-common-styling/` except changes the user agreed to (e.g. the root `.gitignore`). Never commit to or push `master` from this work (`RULES.md` §5.4, §10.4). A broad find-and-replace or a mis-scoped script is the realistic way this goes wrong — not a deliberate decision.
- **No unsafe dynamic-output patterns in generated Liquid or JS.** Flag: `{{ ... }}` output that bypasses Liquid's default HTML-escaping for anything not already known-safe static markup; `.innerHTML =`/`insertAdjacentHTML(...)` fed by anything other than a string this codebase fully controls (component names, fixed template pieces) — never by field content that could ever originate from outside this repo; `eval()`, `new Function(...)`, or a dynamically-constructed `<script src>`. This is a low-probability risk here (an docs site that is installed with the module on every instance, though it renders no user input), but the doc site does build strings dynamically (code snippets from live DOM, icon names from config) — worth a quick scan whenever that code path changes.
- **No new external resource or dependency without confirmation.** Adding a `<script src>`/`<link>` pointing at an external domain, a new `npm` package in `package.json`, or any fetch/API call to a host outside platformOS's own infrastructure is a **consequential change** (`RULES.md` §5.5) — confirm with the user first, same as a token-value or structural change. The existing external dependencies are Google Fonts (loaded by `init`), `@tabler/icons` (build time only) and the bundled Uppy / EasyMDE / highlight.js — anything new needs confirmation.
- **Destructive or hard-to-reverse git operations still require the standing confirmation.** Force push, `git reset --hard`, history rewrites, and branch deletion are already gated by Claude Code's own Git Safety Protocol — this check exists only to catch the DS-module-specific case of that protocol being routed around indirectly (e.g. a generated script that shells out to git, or a "clean up the branch" request that's actually asking for a destructive op without saying so explicitly).

Output format:
```
Security Review — [change description]
Licensed assets:        Pass / Flagged: ...
Secrets/credentials:    Pass / Flagged: ...
Frozen files untouched: Pass / N/A / Flagged: ...
Unsafe dynamic output:  Pass / N/A / Flagged: ...
New external resource:  Pass / N/A / Needs confirmation: ...
Destructive git ops:    Pass / N/A / Needs confirmation: ...
Verdict: Pass / Needs confirmation before proceeding / Blocked
```

A `Blocked` or `Needs confirmation` verdict means stopping and surfacing the specific finding to the user in plain language before continuing — never silently proceeding past a flagged item and never silently "fixing" it by guessing what the user would want.
